# ビジュアライザーの共通機能モデル（調査からの抽象化・提案）

- 状態: 提案 v0.2、2026-11-12。実装済み仕様ではない。
- 製品仕様の正本: [spec.md](spec.md)。§5は基準コミットの検証用抜粋であり、規範の複製ではない。変更時は必ずリンク先の正本を優先する。
- 根拠: [リファレンスDB](references/index.md)。本書の機能分割・検証条件は比較を踏まえた本プロジェクトの設計上の抽象化であり、各参考製品すべてが同じ構造を実装しているという意味ではない。
- 改善への採否: [改善仕様案](improvement-spec.md)。参考製品にある機能を自動採用しない。

## 1. 共通パイプライン

入力 → 時刻・再生状態 → 音特徴抽出 → 特徴から映像値への写像 → 描画 → 合成 → 表示／録画／オフライン出力。

保存設定、能力検出、操作と状態照会は横断機能。音楽を計測するアナライザーと、音楽に反応する芸術表現は区別する。計測値の正確さ、映像の魅力、音との対応、フレームの再現性は別々に評価する。

## 2. 機能契約テンプレート

各機能を実装仕様に落とすときは、以下を埋める。未定の欄は「未定・決定条件・影響先」と記し、実装者の推測で埋めない。

1. ID・目的・対象入力モード・出典ID。
2. 入力: 型、単位、値域、時刻基準、更新頻度、所有権、欠損の意味。
3. 出力: 型、単位、値域、利用可能性、エラー／機能低下の状態。
4. 状態: 初期値、更新則、リセット条件、キャッシュの有効範囲。
5. 設定: 型、既定値、境界値、検証とクランプ／拒否方針、保存対象。
6. 検証: 入力データ、操作列、期待値、許容誤差、実行環境、証拠の保存先。
7. 互換性: 既存設定、ライブとオフライン、非対応環境、解除／破棄時の扱い。

## 3. 機能別の境界と検証項目

| ID | 機能 | 入出力と状態の責務 | 最低限の検証 |
|---|---|---|---|
| CAP-01 | 入力管理 | ファイル／マイク等を区別し、利用可能性・排他・開始失敗・終了を通知。音を二重出力しない | 不正形式、拒否、入力消失、再接続、入力切替で旧接続が残らない |
| CAP-02 | 時刻とトランスポート | 音声時刻、表示時刻、解析窓の時刻を区別。再生・一時停止・停止・シークに対する状態遷移を定義 | 同じ区間の再生、逆向きシーク、連打、中止後再実行。時刻の飛びで履歴が混ざらない |
| CAP-03 | 特徴抽出 | 波形、帯域、ラウドネス、オンセット、拍等に単位と有効フラグを付ける。0と未取得を混同しない | 無音、正弦波、インパルス、クリック列、片チャンネル入力、欠損。推定拍と真値を区別 |
| CAP-04 | 写像・変調 | 正規化、ゲイン、平滑化、範囲、曲線、制限を明示して音特徴を描画値に変換 | 下限／上限、NaN、不連続、急変、フレームレート変更時の一致 |
| CAP-05 | 描画 | 特徴と時刻・seedから画像を生成。解析やUIに直接依存せず、利用可能な機能を宣言 | 空データ、サイズ0、再サイズ、null特徴、同入力の繰返し。2D契約は既存renderer-contractを参照 |
| CAP-06 | シーン・合成 | 層順序、ブレンド、背景、切替と残像、リセットを決める。全曲先読みと因果的ライブ処理を区別 | 切替途中の停止、再シーク、透明度境界、非対応組合せ、旧プリセット読込 |
| CAP-07 | 出力 | 観賞、実時間録画、オフライン生成を別の能力として示し、形式・FPS・音声・キャンセルを扱う | 先頭／末尾、A/V同期、失敗後の再実行、出力形式、途中中止、長時間メモリ |
| CAP-08 | 保存・操作 | 設定スキーマ、移行、実効状態と保存値を区別。UI以外から操作する場合も同じ検証を通す | 不正JSON、未知ID、旧版、読み戻し一致、非対応操作の明示拒否 |
| CAP-09 | 性能・安全な機能低下 | ハード／API能力と計測条件を明示。表示停止や失敗を成功扱いしない | p95描画時間、メモリ、APIなし、GPU context loss、点滅抑制設定 |

## 4. 現在実装に接続する際の境界

- [2D描画契約](renderer-contract.md)のframe/featuresは既存の正本を用いる。新しい抽象化を理由に型を無断変更しない。
- ライブとオフラインの「同じ」は、同じ設定だけでなく、入力、解析コード、時刻、seed、履歴初期化、FPSと比較許容差を指定して初めて検証可能になる。
- GPUの事前解析をライブ入力にも使えるとみなさない。未対応なら能力として明示し、別途因果的な設計を行う。
- 参考製品のソースやプリセットを取り込む場合、公開閲覧可能であることと再配布できることを分けて確認する。本書は実装コードの採用を承認しない。

## 5. 現行2Dに適用できる具体契約（確認済み・基準時点の抜粋）

基準は main `1cafe8e2fba50ceec645be06e40b45a1e9aeb039`。これは新APIの提案ではなく、既存コードを実装者が検証できる形へ整理したもの。GPUには流用しない。定数を変更するときの正本は [Phase16計画](20260928-plan-phase16-music-feature-stream.md) と [renderer-contract](renderer-contract.md) である。

### CAP-03/05: フレーム受渡し

| データ | 現行型・意味 | 利用側の条件 |
|---|---|---|
| `freq` | `Uint8Array`、0〜255、50〜15000 Hzのスライス。表示用のdB由来量であり線形振幅ではない | null/空を防御。解析原値とAGC適用後の描画値を区別 |
| `time` | `Uint8Array \| null`、中心128の波形 | nullを無音128の取得済み波形と同一視しない |
| `features` | `MfsFrameView \| null`、32帯域、12クロマ等。フレーム間で再利用 | 読取専用、保持・変更しない。null時はfreq/beatだけで動作 |
| `dtMs, nowMs` | 数値、ミリ秒。前者は更新間隔、後者は呼出元の時刻 | 外部の現在時刻を描画中に再取得しない。オフラインでは呼出元が合成時刻を与える |
| `getLayer(i,count)` | `Uint8Array`の共有ビュー（入力なしではnull） | `0 ≤ i < count`。ビューを変更・フレーム越し保持しない |

根拠: [FramePipeline](../js/frame-pipeline.js)、[MfsFrameView](../js/mfs-view.js)。MFSのFFTは2048、hopは512サンプルなので、更新間隔は `512/sampleRate` 秒。描画FPSと特徴更新周波数は同一でない。例: 48000 Hzなら約10.667 ms/特徴更新。定数・配置は [mfs-const.js](../js/mfs-const.js) を参照。

### CAP-04: 値の変換と検証可能な更新則

1. **AGC（現行）**: legacy dB範囲は−100〜−30。補正量 `a=round(agcDb*255/70)`、各binは `out[k]=min(255,max(0,in[k]+a))`。線形振幅への乗算ではない。`autoGain`無効またはfeaturesなしなら入力をそのまま使う。補正後は履歴・レイヤー・描画へ流すが、従来BeatDetectorは補正前を使う。
2. **線形レイヤー（現行）**: 長さL、層数C、層iの区間は `[floor(i*L/C),floor((i+1)*L/C))`。例 L=10,C=3 → [0,3),[3,6),[6,10)。切り出しはコピーでなくsubarray。
3. **melレイヤー（現行）**: `mel(f)=2595*log10(1+f/700)`、50〜15000 Hzをmel空間で等分し逆変換、binはroundで算出。各層最低1binを確保し末尾分も残す（L≥Cが前提）。sampleRate/fftSizeがない場合は線形へフォールバック。この層分割は画面の対数周波数軸とは別。
4. **色相（現行）**: 初期位相0、`phase=(phase+speed*0.5*dtMs/16.7)%360`、`effectiveHue=(hue+phase)%360`。無効時は位相を進めない。例 speed=1、dt=16.7なら0.5°増分。
5. **残像（現行）**: intensity≤0は全面背景、正なら `alpha=0.7^intensity` で背景を重ねる。これは**フレームごとの減衰でFPS非依存ではない**。同時間でもFPSが違えば残り方が違うため、再現比較はまず同FPSとする。FPS補正の導入は別途採否判断が必要。

根拠: [mfs-view.js](../js/mfs-view.js) の applyAutoGain/computeLayerRange、[FramePipeline](../js/frame-pipeline.js) の render/_clearWithAfterimage。

### CAP-02/06: 履歴・破棄・リセット

- 現行history容量は `min(240,max(2,round(clamp(historySeconds??4,1,8)*historyFps)))`。例4秒×60fps=240、8秒×60fpsでも240であり「8秒必ず保持」ではない。
- pushはコピー。age=0が最新、範囲外はnull。容量変更では作り直し、長さ変更でも履歴消去。型切替は旧renderer.dispose→新renderer生成・onResize→履歴clear。
- `FramePipeline.reset()` は色相・履歴・beat・物理状態をリセットするが、**既存stateful renderer自身を再生成しない**。再現開始時はrenderer固有状態も含む初期化が必要で、resetだけで完全再現するとは断定しない。
- 呼出順はAGC→タイプ同期→背景/動画（selfClear除外）→色相→描画。GPUはこの経路を使わない。

根拠: [history-buffer.js](../js/history-buffer.js)、[FramePipeline](../js/frame-pipeline.js)。

### 検証ベクトル（追加試験の要求・今回未実行）

| ID | 入力・操作 | 期待結果 |
|---|---|---|
| V-01 | AGC入力[0,100,250]、+7dB | [26,126,255]、入力配列は変更しない |
| V-02 | L=10,C=3の線形分割 | 上記3区間、全binを一度ずつ覆う |
| V-03 | autoGain=true、features=null | 入力freqと同じ値。機能低下であり解析成功と表示しない |
| V-04 | hue=10,speed=1,dt=16.7を2回、他の自動変化なし | effectiveHue=10.5,11。reset後の1回目10.5 |
| V-05 | capacity=2,frameLength=2へ[1,2],[3,4],[5,6]をpush | size=2、get(0)=[5,6],get(1)=[3,4],get(2)=null |
| V-06 | intensity=1、同じ背景を1回重ねる | alpha=0.7。30fpsと60fpsの残像一致は要求しない |

整数配列・区間は完全一致、上記の単純浮動小数計算は絶対誤差1e-9を提案する。画像・音響指標の誤差へこの値を流用しない。

## 6. まだ決めていない共通契約

§5は2Dの既存契約であり、すべてのCAPが完成した実装仕様ではない。入力状態の共通enum、GPU/2D共通の音時刻原点、録画A/V許容差、画像比較の許容差、性能測定端末・予算、設定移行の新スキーマは未確定。現行仕様を継承する部分と、新たに決める部分を[改善仕様案](improvement-spec.md)で分ける。未知の性能値や画質閾値を便宜的に数値化して合格条件にしない。

## 2. 文書体系と SSOT ルール

### 2.1 文書の役割分担

| 文書 | 役割（ここにだけ書く内容） |
|---|---|
| `doc/spec.md` | 製品要件・ユーザーから見える振る舞い・固定方針 |
| `doc/20260928-plan-phase15-test-foundation-and-frame-pipeline.md` | Phase 15 の設計・チケット・テスト |
| `doc/20260928-plan-phase16-music-feature-stream.md` | Phase 16 の設計・**定数表**・アルゴリズム・チケット・テスト |
| `doc/20260928-plan-phase18-song-map-and-auto-director.md` | Phase 18 の設計・**定数表**・アルゴリズム・チケット・テスト |
| `doc/renderer-contract.md` | レンダラーが受け取る `frame` の契約 |
| 本書 | 作業手順・規約・完了条件・質問の仕方 |
| `log.md` | 作業の記録（事実のみ。設計判断の根拠は計画書側へ） |

### 2.2 SSOT の運用規則

1. **同じ事実を2か所に書かない。** 他文書の内容が必要な場合は「`文書名` §番号 を参照」と書く
2. **定数は計画書の定数表が正。** コードの定数名・値は計画書の表と完全一致させる。値を変える場合は、先に計画書を更新する PR を出し、承認後にコードを変える
3. **アルゴリズムは計画書の擬似コードが正。** 擬似コードと異なる実装（高速化など）をする場合は、出力が擬似コードと一致することをテストで示す。一致しない変更は仕様変更として扱う（§6）
4. 計画書に書かれていない振る舞いを**推測で決めない**（§6 の質問プロトコルに従う）
5. 文書間で矛盾を見つけたら、実装を止めて報告する。優先順位は `spec.md`（要件）＞ 計画書（設計）＞ 本書（手順）

## 5. 作業フロー

### 5.1 1チケット = 1ブランチ = 1PR

1. チケット ID を確認する（例: `T16-04`）。前提チケット（計画書のチケット表「前提」列）がマージ済みであることを確認
2. `main` から `impl/<チケットID>-<英小文字ハイフン区切りの短い説明>` ブランチを作成（例: `impl/T16-04-tempo-tracker`）
3. 実装 → テスト追加 → `node tests/run.mjs` 全件パス
4. `log.md` に記録を追加（§8.2 の形式）
5. PR を作成。タイトルは `[T16-04] テンポ推定と拍位相追従`、本文に §7 の完了条件チェックリストを貼り、各項目にチェックを入れる
6. レビュー指摘に対応し、承認後にマージ

### 5.2 コミット

- メッセージは `feat(T16-04): ...` / `test(T16-04): ...` / `docs(T16-04): ...` / `fix(T16-04): ...`
- 1コミットで1つの論理的変更

## 6. 質問・仕様変更プロトコル

以下のどれかに当たったら、**実装を止めて質問する**。自己判断で進めた実装はレビューで差し戻す。

- 計画書に書かれていない振る舞いを決める必要がある
- 計画書の定数・擬似コードどおりに実装すると受け入れテストに合格しない
- 文書間の矛盾を見つけた
- 不変条件（§3）に抵触しそうな実装しか思いつかない

**質問の出し方**: GitHub Issue をタイトル `[質問][T16-04] <要点>` で作成し、次の4点を書く。

1. 該当箇所（文書名 §番号）
2. 何が不明・矛盾しているか
3. 取りうる選択肢（2つ以上）と、それぞれの影響
4. 推奨案とその理由

回答によって計画書を直す場合は、回答者（アーキテクト）が計画書を更新する。実装者は更新された計画書に従う。

## 7. 完了の定義（Definition of Done）— PR 本文にコピーして使う

```md
- [ ] チケットの「成果物」をすべて作成した
- [ ] チケットの「受け入れテスト」をすべて実装し、`node tests/run.mjs` が全件パスした
- [ ] 既存テストを削除・スキップ・閾値緩和していない
- [ ] `node --check` が全 JS ファイルで通る
- [ ] `index.html` を `file://` で直接開き、コンソールエラー 0 を目視確認した
- [ ] 定数名・値が計画書の定数表と一致している
- [ ] 毎フレーム実行されるコードで新しい配列・オブジェクトを生成していない（§9.3）
- [ ] 振る舞いが変わる場合、`doc/spec.md` と `README.md` を更新した
- [ ] `log.md` に記録を追加した
- [ ] 計画書にない判断をしていない（した場合は Issue 番号: #___）
```

ゴールデンフレーム（Phase 15 で導入する見た目の回帰テスト）の基準画像を更新する PR では、上記に加えて「更新理由」と「更新前後の比較画像」（テストランナーが出力する）を PR に添付する。

### 8.1 `doc/spec.md` / `README.md`

ユーザーから見える振る舞いが変わるチケットでは必ず更新する。計画書の各チケットに「spec 更新: 要/不要」を明記してある。

### 8.2 `log.md`

リポジトリ直下 `CLAUDE.md` の「ログフォーマット」（作業内容 / spec.md 変更 / 備考）に従い、先頭（最新が上）に追記する。見出しは既存の `log.md` に合わせて `## YYYY-MM-DD — [チケットID] タイトル` とし、既存ログと同じく「作業内容」の後に「検証」節を置いて、実行したテスト ID と結果を書く。「作業内容」にはファイル単位の変更点を書く。

## 9. コーディング規約

### 9.1 アプリ本体（`js/`）

| 規則 | 内容 |
|---|---|
| スクリプト形式 | **classic script**（`import`/`export` 禁止）。`index.html` に `<script src>` で読み込み順を明示する |
| 公開方法 | トップレベルの `class` / `function` / `const` で宣言する。ファイル末尾に Node テスト用の `if (typeof module !== 'undefined' && module.exports) { module.exports = {...}; }` を付ける（既存 `js/vis-utils.js` と同じ） |
| 禁止構文 | `#private` フィールド（既存方針） |
| コメント | 日本語。ファイル冒頭に「目的 — 参照文書 §番号」を1行書く |
| 命名 | クラス `PascalCase`、関数・変数 `camelCase`、定数 `UPPER_SNAKE_CASE`、非公開メソッド `_camelCase` |
| AudioWorklet 内で動くコード | 外部の関数・グローバル変数を参照しない**自己完結クラス**にする（`toString()` でワークレットソースへ埋め込むため。既存 `js/fft.js` と同じ方式） |
| 乱数 | 描画・解析・演出で `Math.random()` を使わない。`makeRng(seed)`（`js/vis-utils.js`）を使う（決定性のため。UI のランダムボタンのみ例外） |
| 時刻 | 描画・解析のロジック内で `performance.now()` / `Date.now()` を直接呼ばない。呼び出し側から時刻を引数で受け取る（テストで時刻を固定するため） |

### 9.2 テスト（`tests/`）

- Node 単体テストは `node:test` と `node:assert/strict` を使い、ESM（`.mjs`）で書く
- アプリ本体のファイルは `tests/lib/load-classic.mjs`（Phase 15 で作成）で読み込む。テストのためにアプリ本体へ `export` を追加しない
- テスト ID（例: `U16-05`）をテスト名の先頭に書く: `test('U16-05 テンポ推定: 120BPMクリック', ...)`
- 乱数を使う合成信号は必ずシード固定

### 9.3 性能ルール

- `requestAnimationFrame` と AudioWorklet の `process()` から呼ばれる経路では、配列・オブジェクト・クロージャを新しく生成しない。バッファは constructor / 初期化時に確保して使い回す
- 例外: 計画書で「毎フレーム生成可」と明記した箇所のみ

## 10. 難易度表記

計画書のチケット表の「難易度」列は、推奨される経験の目安。

| 表記 | 目安 | 例 |
|---|---|---|
| ★1 | 実務1〜2年。既存コードの模倣で完結 | UI 追加、テスト追加、文書更新 |
| ★2 | 実務3年以上。複数ファイルにまたがる設計の理解が必要 | 新規モジュール、パイプライン統合 |
| ★3 | 信号処理、Web Audio、非同期処理のいずれかの実務経験 | テンポ推定、AudioWorklet、描画パイプラインのリファクタ |

★3 のチケットは、着手前に設計の読み合わせ（計画書の該当節を実装者が自分の言葉で要約して PR 下書きに書く）を推奨する。
